## Purpose
This runbook covers the response to connection pool exhaustion on payments-ledger-db, the recurring root cause behind INC-2025-019, INC-2025-041, and INC-2026-013. It is referenced from RB-001 as a sub-procedure for gateway degradation triage.

## Detection
An automated alert fires when connection pool utilisation exceeds 80% for more than 2 minutes, implemented following INC-2025-041. Prior to this alert existing, exhaustion was typically first noticed through elevated orchestrator error rates rather than proactively.

## Steps
1. Check current pool utilisation on the payments-ledger-db dashboard.
2. Identify whether batch, reporting, or analytics queries are running against the primary; if so, redirect them to the read replica immediately.
3. If utilisation remains above 90% after redirecting non-critical load, request a temporary pool size increase from the database team, capped at 300 connections without further architecture review.
4. Kill any individual long-running query older than 5 minutes that is not a customer-facing transaction, after confirming with the DBA on call.
5. Monitor for 15 minutes after any mitigation before declaring recovery.

## Escalation
Engage the database on-call immediately upon alert (see services.json for the payments-ledger-db on_call_employee_id). Escalate to SEV1 if pool exhaustion is projected to cause a full outage within 10 minutes based on utilisation trend. Notify Dinesh Wickramasinghe for any incident occurring during a known peak period, such as salary day or festive season, given the recurring nature of this failure mode.

## Rollback
If a temporary pool size increase was applied, revert to the standard size once utilisation has been stable below 60% for at least 24 hours, unless a permanent increase has been formally approved through capacity review, see MTG-2026-014. Do not leave emergency pool sizes in place indefinitely without review, as unreviewed capacity changes can mask underlying capacity planning gaps.
